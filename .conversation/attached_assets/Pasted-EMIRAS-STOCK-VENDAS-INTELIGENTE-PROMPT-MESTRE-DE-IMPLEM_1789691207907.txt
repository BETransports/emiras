EMIRAS STOCK + VENDAS INTELIGENTE

PROMPT MESTRE DE IMPLEMENTAÇÃO — REPLIT

Atua simultaneamente como Software Architect, Senior Full-Stack Developer, Backend Developer, Frontend Developer, Database Architect, UX/UI Designer, Product Manager, QA Engineer e Security Engineer.

Desenvolve um sistema comercial real chamado EMIRAS STOCK + VENDAS INTELIGENTE, destinado principalmente a pequenas e médias empresas em Angola.

O sistema deve ser uma aplicação web full-stack real, funcional, segura, responsiva e preparada para utilização comercial. Não criar protótipos, mockups, botões falsos, dados fictícios apresentados como reais, páginas sem funcionalidade, autenticação simulada, dashboards estáticos ou formulários que não gravem dados.

Todas as ações da interface devem estar ligadas ao backend e ao PostgreSQL. Se uma funcionalidade ainda não estiver implementada, não apresentar um botão que finja funcionar. Implementar corretamente ou identificá-la claramente como futura.

2. STACK E PADRÕES TÉCNICOS

Utilizar, preferencialmente:

- Frontend: React, TypeScript e Vite
- UI: Tailwind CSS e componentes reutilizáveis
- Backend: Node.js e TypeScript
- API: REST ou arquitetura equivalente bem estruturada
- Banco de dados: PostgreSQL
- ORM: Prisma ou alternativa moderna adequada ao Replit
- Autenticação: sessões ou tokens seguros, com passwords protegidas por hash
- Infraestrutura: Replit, PostgreSQL integrado/disponível e variáveis de ambiente

Separar claramente:

- frontend
- backend
- database
- authentication
- business logic
- API
- components
- pages
- services
- validation
- utilities
- tests

Evitar código duplicado e componentes gigantes. A arquitetura deve permitir adicionar módulos futuros sem reescrever o sistema.

---

3. REGRAS GERAIS DE IMPLEMENTAÇÃO

1. Segurança tem prioridade sobre design.
2. Integridade dos dados tem prioridade sobre velocidade de desenvolvimento.
3. Toda regra crítica deve ser validada no backend.
4. Nunca confiar apenas no frontend para autorização ou isolamento de dados.
5. Todas as operações assíncronas devem possuir loading state.
6. Todas as páginas devem possuir estados vazios úteis.
7. Listagens grandes devem utilizar paginação ou carregamento eficiente.
8. Erros técnicos devem ser registados nos logs, mas mensagens compreensíveis devem ser mostradas ao utilizador.
9. Não utilizar localStorage ou dados no navegador como substituto do banco.
10. Não utilizar números hardcoded no dashboard.
11. Não declarar uma etapa concluída sem verificar arquivos, banco, APIs, erros e fluxos principais.
12. Após cada fase, executar os comandos de validação definidos e corrigir os problemas encontrados.

3. definir quantidade

5. remover produto
6. aplicar desconto quando autorizado

9. calcular total
10. selecionar método de pagamento
11. confirmar venda
12. criar venda
13. criar itens vendidos
14. atualizar stock
15. criar movimentos de stock
16. mostrar confirmação

- Multicaixa
- Outro

- cartão
- pagamentos digitais
- outros métodos

Número da venda

EM-2026-000001

Integridade transacional

Ao confirmar uma venda:

1. validar utilizador
2. validar empresa
3. validar produtos
4. verificar stock
5. calcular valores no backend
6. criar venda
7. criar itens
8. atualizar stock
9. criar movimentos
10. concluir transação

Se qualquer etapa falhar, reverter tudo.

Critérios de aceitação

- O total é recalculado no backend.
- O frontend não consegue manipular o preço final de forma indevida.
- Não é possível vender produto inativo.
- Não é possível vender quantidade inválida.
- Não é possível vender acima do stock disponível.
- A venda, os itens, a atualização de stock e os movimentos são atómicos.
- Não existe venda sem atualização de stock.
- Não existe atualização de stock de venda sem movimento correspondente.
- Cliques repetidos não criam vendas duplicadas.
- A venda pode ser associada a cliente ou ficar sem cliente.
- O desconto respeita permissões.
